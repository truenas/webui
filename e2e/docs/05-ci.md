# E2E in CI — how the pipeline works, what it needs, what it taught us

**Status:** running and green, 2026-09-02. `.github/workflows/e2e.yml`,
`e2e/ci/appliance.sh`.

`status.md` says where the suite is; `04-environment-architecture.md` is the
design for where the environment goes. This file is the operational record of
the pipeline that exists: the shape, the lab prerequisites, the numbers, and the
failures it took to get there, so nobody pays for them twice.

---

## The shape

One job, on a self-hosted runner that is itself a **TrueNAS box**. Per run:

1. **Checkout and install** with the shared
   `iXsystems/ux-github-workflows/.github/actions/prepare` action, with `TMPDIR`
   pointed at the runner's work directory (see *Lessons*, `/tmp` is noexec).
2. **Resolve the browser image.** `mcr.microsoft.com/playwright:v<version>-noble`,
   the version read from the installed `@playwright/test` so the two cannot
   drift. Docker is reached directly or through `sudo -n docker`, whichever
   works; a runner with neither fails here, before anything is provisioned.
3. **Build the UI.** `yarn build:prod`, the same production build as
   `main.yml`, with `--base-href /ui/`. The UI under test is this checkout's,
   not the one baked into the ISO. Built before the claim so the lab is not
   held during the build and the build's memory is back before the guest
   starts.
4. **Claim an appliance.** `appliance.sh claim fresh-install` drives
   `tn_guest.py` (iXsystems/api-ci-testbed) against the box's own middleware
   API. With a template on the host it **clones** it: middleware's `vm.clone`
   copies the VM record, its UEFI NVRAM and every zvol from the template's
   snapshot, the script rewrites the clone's ports, boots it, waits for the
   API and rotates the admin password to a per-run one. With the template
   password configured but no template on the host, it builds one first,
   once; without the password it installs from the ISO. Either way it prints
   the suite's `TN_*` variables, which the workflow masks and loads into the
   job environment.

   The template is a bare install, shut down after first boot and
   snapshotted, built weekly by `e2e-template.yml` with
   `appliance.sh build-template`. It is E5 of the design in its first form.
5. **Serve the UI.** A stock `nginx` container with `dist/` mounted and the
   repository's own `docker/nginx.conf`, the file the appliance serves the UI
   through: `/ui/` from disk, the API paths proxied to the appliance's
   forwarded port 80 through Docker's host gateway. Over TLS with a throwaway
   self-signed certificate, because a production build ignores the login
   token on a plain-HTTP origin. Published on an ephemeral loopback port.
   Host networking is not an option: nginx binds the ports the TrueNAS host's
   own UI is on. The step checks both the UI and the proxy answer before
   handing over.
6. **Run the suite** inside the Playwright container with `--network host`,
   reusing the host's `node_modules`. The profile is `shipped` with
   `TN_UI_BASE_URL` pointing at the served UI: it *is* the production build
   at `/ui/` over https, just not from the appliance, and that profile is the
   one that tolerates a self-signed certificate. Credentials reach the
   container through an `--env-file` on the runner's dataset, never on the
   command line.
7. **Upload JUnit**, always, and **traces, screenshots and video** for failed
   tests. Publishing traces is safe because the credential they contain is
   per claim and the appliance is destroyed at release; do not copy that
   upload into a pipeline that reuses either.
8. **Stop the UI container and release the appliance**, unconditionally:
   `tn_guest.py delete`. A claim that died before the workflow recorded the
   name is still released, because `claim` writes the nickname to a file first
   and `release` falls back to it.

`workflow_dispatch` takes `ui: shipped` to run against the UI baked into the
ISO instead.

## When it runs

| Trigger | Why |
|---|---|
| Nightly, 03:00 UTC | Master's UI against the configured ISO, which is one fixed nightly until rotation exists (see *Next*). |
| Push to master touching `src/`, the suite, `playwright.config.ts`, the lockfile or the workflow | Every merged UI change gets a run. |
| Pull request touching the suite or the workflow, same-repo only | Changes to the tests and the pipeline prove themselves. |
| `gh workflow run e2e.yml --ref <branch>` | The opt-in for any other branch. Not every PR: one runner, one appliance, ~8 minutes a run, and a concurrency group that holds one pending run, so under normal PR volume most pushes would never run and nobody could tell which. |
| `e2e-template.yml`, weekly on Sunday 01:00 UTC, or dispatched | Rebuilds the template from the ISO. Same concurrency group, so it never races a run. |

The appliance sits behind QEMU user-mode NAT (`hostfwd`): its ports 80 and 443
are forwarded to a per-deployment port pair on the host, so the suite's target
is `localhost:<https port>`, and both the UI and the middleware socket go
through the forwarded 443. Nothing else reaches the guest, which is why there
is no SSH and no middleware log collection in this mode.

## What the lab has to provide

On the runner box, outside this repository:

| Thing | Where | Notes |
|---|---|---|
| Runner | `/mnt/tank/github/actions-runner` | Label `truenas-lab`. Runs as a non-root user with `sudo -n docker` allowed. |
| api-ci-testbed clone | `/mnt/tank/github/api-ci-testbed` | `jenkins/scripts/tn_guest.py` is what is called. |
| Python venv | `/mnt/tank/github/venv` | Needs `truenas_api_client`, `aiohttp`, `requests`. |
| Install ISO | `/mnt/tank/iso/<name>.iso` | Must be in a **child dataset**, world-readable. A directory in the pool root is rejected. Must be a **v27 nightly** (below). |
| Docker | Apps configured with a pool | dockerd only runs once Apps has a pool. |
| Virtualization | CPU extensions exposed to the box | If the box is itself a VM, nested virtualization must be on, or `vm.create` fails with "does not support virtualization". |
| API account | user with **Full Admin** | An API key inherits its user's roles; a plain user authenticates and then gets `EACCES` on `vm.create`. |

In the repository's `e2e-lab` environment:

| Kind | Name | Meaning |
|---|---|---|
| variable | `E2E_TN_GUEST_ISO` | Host path of the ISO. |
| variable | `E2E_TN_GUEST_HOST_USER` | The API account. |
| variable | `E2E_TN_GUEST_POOL` | Pool for VM datasets and zvols. Default `tank`. |
| secret | `TN_GUEST_HOST_API_KEY` | Key for that account. `TN_GUEST_HOST_PASSWORD` works instead. |
| secret | `TN_GUEST_TEMPLATE_PASSWORD` | Admin password baked into the template. Set: claims clone the template and rotate away from it. Unset: every claim installs from the ISO. |
| variable | `E2E_TN_GUEST_TEMPLATE` | Template nickname. Default `e2e-template`. |

Guest sizing lives in `appliance.sh` as environment overrides: 6GB RAM,
4 vCPUs, 10GB OS disk, ten 10GB data disks (sparse zvols, so the count is free
until written). The pool journey needs at least nine identical unused disks,
and the zvols come out with distinct serials, which the pool wizard requires.

## Numbers

Measured on the lab box, 2026-09-02:

| Step | Time |
|---|---|
| Install from a v27 nightly ISO to API ready | ~3.5 min |
| Install from the 25.10.7 release ISO to API ready | ~10 min |
| Suite, four tests, one worker | ~1.5 min |
| Whole job, checkout to release | ~6 min |

The 25.10 figure is not directly useful (the suite cannot run against 25.10,
see below) but it is the honest floor for "reinstall as the restore primitive"
on a release image, which the design's 210s assumed.

## Lessons, each one a failed run

- **`/tmp` is noexec on TrueNAS.** Yarn packs the one git dependency by writing
  a `yarn` shim into a temp directory and running it. On noexec `/tmp` the shim
  cannot execute, PATH lookup falls through to corepack, corepack finds no
  pinned package manager in the clone and downloads Yarn 1, and Yarn 1 builds a
  different archive from Yarn 4 — so `yarn install --immutable` fails with a
  checksum mismatch on this runner only. `TMPDIR=$RUNNER_TEMP` is the fix.
  A wrong archive, once fetched, is kept in yarn's global mirror in the runner
  user's home and served on every later run without repacking; clear it if
  the symptom outlives the cause.
- **`playwright install --with-deps` needs sudo, and sudo prompts.** The job
  hung on a password prompt until its timeout. The browser now comes from
  Playwright's image; the runner never installs it.
- **ixnode is not usable here.** It is the legacy tool for dedicated Debian KVM
  hosts and needs libvirt, `virt-install`, a `/data` tree and root. The same
  repository's `tn_guest.py` is built for a TrueNAS host and was the right
  tool from the start.
- **The host crashed twice mid-install** with an 8GB guest. 6GB has been
  stable. A box that is itself a VM needs the guest's RAM plus its own plus
  headroom for the runner, Docker and Chromium.
- **A crash leaves an orphan.** A VM record can survive without its dataset;
  tn_guest allocates names from datasets, so the next run picks the same name
  and `vm.create` fails with "name already exists". Delete the VM under
  Virtualization. `prune` cannot see it.
- **The ISO has three layout rules**, each enforced by middleware at CD-ROM
  attach time, after the VM exists: inside a child dataset (not the pool root),
  readable by `libvirt-qemu`, and not under the runner user's private
  directory. `appliance.sh` checks the file exists before provisioning;
  middleware checks the rest.
- **A 25.10 appliance fails the suite at the first API call.** The suite is
  typed against API v27; a release appliance advertises v25.10.x and the
  client refuses the year mismatch by design. Use a master nightly ISO.
- **Credentials on a command line are logged.** With `sudo -n docker`, every
  argument is written to the sudo log. Pass them through `--env-file`.
- **A bare `self-hosted` label matches this runner too.** The `main.yml`
  unit-test job used one and landed on the lab box, where it failed. It now
  selects `[self-hosted, Linux, ARM64]`. Any future self-hosted job needs a
  label this runner does not carry.

## Next

- **Rotate the ISO.** `E2E_TN_GUEST_ISO` names one nightly file, which goes
  stale; the nightly run then tests master against an ageing appliance.
  Deliberately deferred: how the box gets nightlies is still to be decided.
- **Read Q0b off the clone.** A clone's boot-to-API time is most of the
  rollback cycle the design's *Sequence* step 2 wants measured; the claim
  step's timing now gives it on every run. Record it in the design doc and
  decide per-test restore on it.
- **Remember the template ages with its ISO.** It is rebuilt weekly from
  whatever `E2E_TN_GUEST_ISO` names; ISO rotation (above) is what would make
  that a fresh nightly each week.
- **Middleware logs.** Behind `hostfwd` there is no SSH; collection needs an
  API route.
- **Snapshot restore** (`04-environment-architecture.md`, E1/E5) is now ours to
  build, not another team's: on a TrueNAS host the primitive is a ZFS snapshot
  of the deployment's zvols with the VM stopped, and a rollback plus boot. That
  is the design's disk-only row. Memory-state snapshots are not exposed by the
  VM API.
