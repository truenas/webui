# E2E in CI — how the pipeline works, what it needs, what it taught us

**Status:** running and green on runner-attached appliances, 2026-10-12
(run 38281104721: 75 passed, 6 skipped). `.github/workflows/e2e.yml`, the
`truenas-appliance-runner` action in iXsystems/ux-github-workflows, and the
GARM provider and appliance image in iXsystems/github-truenas-runner, whose
`docs/e2e-appliances.md` is the design and the record on that side.

`status.md` says what the suite assumes and cannot do;
`04-environment-architecture.md` is the design for where the environment goes.
This file is the operational record of the pipeline that exists: the shape, the
prerequisites, the numbers, and the failures it took to get there, so nobody
pays for them twice.

Until 2026-10-12 the pipeline claimed an appliance from a lab box instead;
[Before: the lab claim](#before-the-lab-claim) keeps what that taught.

---

## The shape

**The appliance is inside the runner.** Each job runs on an ephemeral runner
that GARM makes on a TrueNAS box, from a scale set whose extra specs attach a
second disk: a copy-on-write clone of a prebuilt TrueNAS appliance image
(`truenas_appliance:nightly`). The job boots that disk under qemu, inside the
runner, with nested KVM. Picking the runner label is the claim; GARM deleting
the runner when the job ends is the release. Nothing is shared between runs,
so nothing can leak into the next one.

Per run. Steps 3 and 5–7 and 9 are local composite actions under
`.github/actions` — `e2e-browser`, `webui-dist`, `e2e-serve-ui` and `e2e-run`,
and step 4's license comes from `fetch-license` — which `e2e-ha.yml`, the HA
suite's workflow, runs too; the workflow files hold only what is particular
to each.

1. **Plan.** A small job on `ubuntu-latest` turns the `shards` input into the
   matrix. Every other job is one shard. It is 2 by default, and on every run
   that is not a dispatch; a dispatch can ask for more or fewer. Playwright
   splits by test count, not time, in file order, so the halves are only
   roughly even: by 2026-10-21 timings, about 42 and 49 minutes of tests.
2. **Checkout and install** with the shared
   `iXsystems/ux-github-workflows/.github/actions/prepare` action.
3. **Resolve the browser image** (`e2e-browser`). `mcr.microsoft.com/playwright:v<version>-noble`,
   the version read from the installed `@playwright/test` so the two cannot
   drift. A runner without a usable Docker fails here, before the appliance
   boots.
4. **Boot the appliance.** One step, the `truenas-appliance-runner` action.
   It finds the attached disk (the one disk besides the runner's own that
   holds a ZFS `boot-pool`), boots it under qemu on a qcow2 overlay with ten
   sparse 10GB data disks and one sparse 32GB disk after them
   (`extra-disk-gb: '32'`: `boot.attach` needs a disk at least as large as
   the boot disk, which no 10GB disk is), waits for the API, rotates the admin password to
   one made for this job (masked), snapshots the running VM, memory included,
   as `fresh-install`, and puts the suite's `TN_*` variables in the job
   environment. Its ports 80, 443 and 22 are forwarded to the runner's
   loopback and Docker's bridge, nowhere else. `truenas-appliance` is put on
   `PATH`: `revert fresh-install` brings the appliance back in ~6 s,
   `console` shows its serial console.
   The appliance gets **8GB** (`memory-mb: 8192`), not the action's 6GB
   default. Choosing an Apps pool makes middleware clone the whole apps
   catalog into the tmpfs at `/run`, which is sized from RAM. At 6GB that
   filled `/run`, and dockerd could not write its pid file (#14633).
   It also gets **one spare NIC** (`spare-nics: 1`), after the management
   NIC so that one keeps its name. The spare is a virtio NIC alone on a qemu
   hub, with no DHCP, no route and no peer, so it never holds an address of
   its own. Its fixed MAC (`52:54:00:e2:e0:01`) is in `TN_SPARE_NICS`. It
   exists for `network-interfaces-commit.e2e.ts`, which commits VLANs,
   bridges and LAGGs on it. Doing that on the management NIC could cut the
   suite off from the appliance (#14537). The spec skips when
   `TN_SPARE_NICS` is unset. `e2e-run` passes it into the suite's container
   by name with the other `TN_*` variables. It once did not, and run
   `39967521612` was green with all four tests skipped.
   **Then it is licensed**: a non-HA Enterprise license (serial `CI-SINGLE`)
   is fetched from MES's renew endpoint (`fetch-license`, which masks the
   endpoint's host as well as its URL), the same one api-ci-testbed's
   `fetch_license.sh` uses, uploaded with `truenas.license.upload`, and the
   baseline is taken again over the same name so a revert keeps it. Fetched
   every run, never committed: renewing re-signs it with a current
   `issued_at`, and middleware caps a test license's life from that stamp.
   The step logs the entitlements it now grants. This is what lets the
   journeys behind an entitlement (`ZFSTIER`, `S3_AUDIT`, `S3_VERSIONING`)
   run here instead of skipping; it is done in the workflow, not the suite,
   so the PEM never lands in a published trace.
5. **Get the UI** (`webui-dist`). The UI under test is this checkout's, not the one baked
   into the image, and `main.yml`'s Build job has already built it: as the
   Debian package that ships, uploaded as the `webui-dist` artifact. The job
   finds that WebUI run by commit and waits for the upload, only now, after
   the boot, so the build and the boot overlap. It counts only a run that
   built the same tree: for a pull request, the WebUI run of its head
   commit; otherwise the push run of the commit, which the nightly and a
   dispatch on master have. A dispatch on another branch, a failed build, or
   a WebUI run still going after ten minutes means `yarn build:prod` here
   instead (`--base-href /ui/`, the same build).
6. **Serve the UI** (`e2e-serve-ui`). A stock `nginx` container with `dist/`
   mounted and the repository's own `docker/nginx.conf`, the file the
   appliance serves the UI through: `/ui/` from disk, the API paths proxied to
   the appliance's forwarded port 80. Over TLS with a throwaway self-signed
   certificate, because a production build ignores the login token on a
   plain-HTTP origin, and over cleartext beside it for the insecure-connection
   test. On the runner's own network, at two free loopback ports: an HA
   pair's addresses are reachable from there and not from Docker's bridge. The
   step checks both the UI and the proxy answer before handing over.
7. **Run the suite** (`e2e-run`) inside the Playwright container with `--network host`,
   reusing the runner's `node_modules`, with `--shard <i>/<n>`. The profile is
   `shipped` with `TN_UI_BASE_URL` pointing at the served UI: it *is* the
   production build at `/ui/` over https, just not from the appliance, and
   that profile is the one that tolerates a self-signed certificate.
   Credentials reach the container through an `--env-file`, never on the
   command line. Just before it, a step checks that the runner reaches the
   Active Directory test domain's controllers on TCP 53, 88, 389, 445 and 464,
   and warns for each port that does not answer; the appliance, behind qemu's
   NAT, reaches what the runner reaches. The suite step alone is given the
   domain's `TN_AD_*` variables, from the `E2EUI_AD_*` secrets.
8. **On failure or cancellation, what the appliance says**, as folded
   sections of the job log: the console's last 300 lines; `docker.status`
   and `docker.config` over the API; the action's `boot-report`; then over
   ssh, Docker's unit status, its journal and the boot's warnings,
   middleware's log filtered to Docker and Apps (last 300 lines), the
   `ix-apps` datasets of every pool, `df -h /run` and the largest things in
   it, `ip -br addr`, `ip route` and `/etc/docker/daemon.json`.
   `appliance.sh` has no `ssh` of its own, so the step logs in with the key
   `boot-report` leaves behind; no `ssh: true` on the boot is needed. Every
   line taken from middleware or over ssh goes through `grep -iv license`,
   because these logs are public. The console is the exception: it is
   printed unfiltered, as it always was. All of it, the console included,
   then loses every line naming a `TN_AD_*` value in any case: the AD spec's
   refused join logs a traceback with the domain in capitals, which GitHub's
   verbatim masking misses. Cancellation counts because a run at its 120-minute ceiling is
   the one that most needs this; each command is bounded by `timeout`, so
   the step fits the grace period a cancelled job gets.
9. **Upload JUnit** (`e2e-run`), always, and **traces, screenshots and video** for failed
   tests, one artifact per shard. Publishing traces is safe because the
   credential they contain is per job and the appliance is deleted with its
   runner; do not copy that upload into a pipeline that reuses either.
   What would stay valuable after the job is kept out: the test that pastes
   the HA license records nothing, and writes what Playwright keeps anyway to
   its own `outputDir`, outside the `test-results/` this uploads. So does
   every spec under `tests/unpublished/` (the `unpublished` project), which is
   where a test that types a secret outliving the job belongs — today the
   Active Directory test domain's credentials. So a failed
   join leaves its JUnit message in CI and nothing else, with every `TN_AD_*`
   value in it replaced by a placeholder; reproduce locally, where the trace
   is kept.
10. **Stop the UI container.** No release step: the runner, and the appliance
    with it, is deleted when the job ends, on success, failure and
    cancellation alike.
11. **Coverage and timings, once for the run.** Each shard uploads its tests'
    coverage files (`e2e-coverage-<n>`) and timing records (`e2e-timings-<n>`)
    and reports nothing itself, since its reports would count only its own
    tests. A `report` job on `ubuntu-latest` waits for every shard, runs
    `yarn e2e:coverage` over the coverage files in one directory, into the
    run's summary and a notice, and `yarn e2e:timings` over the timing records,
    a directory per shard, into the summary. A shard that never reached the
    suite is called out, not silently left out. The merged files go up as
    `e2e-coverage` and `e2e-timings`.

`workflow_dispatch` takes `shards`, `grep`, and `ui: shipped` to run against
the UI baked into the image instead of this checkout's.

## When it runs

| Trigger | Why |
|---|---|
| Nightly, 03:00 UTC | Master's UI against the newest appliance image. |
| Push to master touching `src/`, the suite, `playwright.config.ts`, the lockfile or the workflow | Every merged UI change gets a run. |
| Pull request touching the suite or the workflow, same-repo only | Changes to the tests and the pipeline prove themselves. |
| `gh workflow run e2e.yml --ref <branch>` | The opt-in for any other branch. |

Runs share nothing, so the concurrency group is per ref: a newer push to a pull
request cancels its older run, and cancelling leaks nothing. Running on every
pull request that touches the UI is the next step, once the scale set's
capacity is measured.

## What it needs

Outside this repository; `docs/e2e-appliances.md` in
iXsystems/github-truenas-runner has the detail.

| Thing | Where | Notes |
|---|---|---|
| The appliance image | the image pipeline in github-truenas-runner | `truenas_appliance:nightly`, built daily from the newest nightly ISO of the series webui master is typed against (now `TrueNAS-28.0.0-MASTER`). |
| The image on a box | that box's provider config | `truenas_appliance:nightly` in `[images] sync`; image-sync imports each new version. |
| A GARM scale set | GARM, **for the `truenas` organization** | Image `debian_tn_linux_zfs`, a flavor with room for the appliance (8GB, 4 vCPUs) and the job, extra specs `{"disks": ["truenas_appliance:nightly"]}`, labels `self-hosted` and `truenas-appliance`. Its max runners is the number of appliances at once. |
| A runner group | the `truenas` organization | `e2e-appliances`: only `truenas/webui`, and **Allow public repositories** checked. |
| GARM's agent URL | GARM | https or wss: `garm-agent` refuses plain http. |
| Outbound HTTPS from the appliance to `images.sys.truenas.net` | the runner's network | The container image registry. `tests/containers.e2e.ts` lists it in the Create form's image browser and has middleware download a Debian rootfs from it; without it those tests fail at the image browser or the create job. |
| Outbound HTTPS from the appliance to `github.com` and `ghcr.io` | the runner's network | The apps catalog, IT Tools' image and BusyBox (`ghcr.io/containerd/busybox`). `tests/apps-install.e2e.ts` syncs the catalog and installs that app; `tests/apps-custom-yaml.e2e.ts` installs a custom app that runs BusyBox and pulls it from Manage Container Images. Without it those tests fail at the catalog sync, the install job or the pull. Every registry throttles anonymous pulls (`toomanyrequests`) — ECR Public, which the custom-app tests used before, failed their installs that way — so those tests pull the image over the API first, retry a throttled pull, and read the image back afterwards, because a pull throttled mid-stream still ends its job `SUCCESS`. Their compose files say `pull_policy: never`, so `up` never reaches a registry. |
| The CI license | MES's renew endpoint, whose full URL is the `E2E_LICENSE_URL` repository secret | Serial `CI-SINGLE`. Internal-only and unauthenticated, so the runner has to reach it, and kept out of this public repository; a run without the secret, or that cannot reach it, fails at the license step. |

| The Active Directory test domain | the internal network; the `E2EUI_AD_*` repository secrets | `E2EUI_AD_DOMAIN`, `E2EUI_AD_DC1`, `E2EUI_AD_DC2`, `E2EUI_AD_USERNAME`, `E2EUI_AD_PASSWORD`, `E2EUI_AD_COMPUTER_OU`, mapped to the suite's `TN_AD_*`. Shared with other automation. The DCs serve the domain's DNS and must be reachable from the runner on 53, 88, 389, 445 and 464; the account must be able to create and delete computer objects in the OU. Without the secrets `directory-services-ad` and `roles-directory-services-ad` skip; unreachable, they fail. |

Two kinds of secret, and no repository environment. `E2E_LICENSE_URL` is an
address, not a credential, kept out of the public repository; the license it
returns is fetched fresh, applied, and never written to disk or the log. The
`E2EUI_AD_*` secrets are the one credential the job holds for something other
than its own appliance, and it outlives the job — so they are given to the
suite step alone, the specs that type them publish nothing, and every value is
a secret so the job log masks it. GitHub gives secrets to no workflow run from
a fork, and the job does not run for one anyway (`e2e.yml`'s header). The
account's reach is the real limit on a leak: it should be able to do nothing
but join computers to the OU and remove them.

## Numbers

Measured 2026-10-12, a TrueNAS 28 appliance on a runner from the `truenas`
organization's scale set (run 38281104721):

| Step | Time |
|---|---|
| qemu start to the API taking a login | 83 s |
| Baseline snapshot (`savevm`, memory included) | 9 s |
| Revert to it (`loadvm` to a login), from the image build | ~6 s |
| Pull the Playwright image (a fresh runner has none) | 112 s |
| Build the UI | 79 s |
| Suite, 81 tests, one shard | 9.8 min |
| Whole job, checkout to the end | 15.5 min |

Against the lab's last run that reached the suite (run 36860948623,
2026-10-01): the 52 tests both runs have took **309 s there and 405 s here**
(×1.31 in total, ×1.71 per test at the median), and the whole job 11.0 against
15.5 min. Not a clean comparison — TrueNAS 27 against 28, and eleven days of UI
and suite changes — and the per-test picture is mixed: UI-heavy journeys got
3–3.8× slower (the user form's submit 3.0 → 11.3 s), the pool tests 3.5×
faster. The likeliest cause of the slowdown is contention: the appliance,
Chromium, nginx and Docker share one runner VM, where in the lab the appliance
had a VM of its own. A run on a bigger flavor tells.

The trade is worth it: the lab's single runner went offline on 2026-10-01 and
no master run reached the suite for eleven days. Here capacity is the scale
set's size, and sharding divides the suite.

## Lessons, each one a failed run

From moving to runner-attached appliances:

- **A public repository's job cannot use an action from a private one**, nor
  from another organization's. The action lives in ux-github-workflows,
  which is public, for that reason.
- **A runner group keeps public repositories out by default.** The job
  waited for a runner forever, labels matching and the scale set online,
  and nothing said why. Allow public repositories on the group, and only on
  a group that holds nothing but these runners.
- **`garm-agent` refuses a plain-http agent URL**, so the runner registered
  with GitHub but never came online, and GitHub assigned it a job nothing
  ran.
- **TrueNAS replaces the serial** a provider gives a VM's disk with a random
  one. The action finds the appliance disk by its `boot-pool`.
- **The appliance must be the version master is typed against.** Master moved
  to 28 while the image built 27, and every test failed at its first API call.
  The suite's refusal of an API year it is not typed against is by design;
  moving `ISO_SERIES` with master is part of moving master.

Still true from the lab:

- **`playwright install --with-deps` needs sudo, and sudo prompts.** The
  browser comes from Playwright's image; the runner never installs it.
- **Credentials on a command line are logged.** Pass them through
  `--env-file`.
- **A bare `self-hosted` label matches every self-hosted runner.** The
  `main.yml` unit-test job once landed on the lab box with one. Any
  self-hosted job needs a label of its own.

## Next

- **Measure the two-shard runs**: what a developer waits for is the slower
  shard, so if the split stays uneven, a third shard or a different file
  order is the lever.
- **The flavor**: one run on a bigger one says whether the slower UI tests are
  contention.
- **Setup per shard**: Playwright's image in the runner image, yarn's cache. (The UI is
  built once now, by `main.yml`, and every shard downloads it.)
- **Use the snapshot.** The suite cleans up after itself, so `fresh-install`
  is taken and never used. A ~6 s revert is the restore E1 and E2 assumed
  would take 60–75 s; it could replace slow cleanup paths, or give a retried
  test a clean appliance.

## Before: the lab claim

Until 2026-10-12, one job on a self-hosted runner that was itself a TrueNAS
box claimed an appliance from it: the `truenas-appliance` action in
ux-github-workflows cloned a template VM through the box's own API with
`tn_guest.py` (iXsystems/api-ci-testbed), held it under a lease, and released
it in a `post` step. One appliance at a time, behind a `concurrency: e2e-lab`
group, with the box's Full Admin key in the `e2e-lab` environment. A clone
reached its API in ~75 s; a whole four-test job took ~5 min. What it taught
that no longer applies, kept for whoever runs a TrueNAS box as a runner again:

- **`/tmp` is noexec on TrueNAS**, and yarn's git-dependency packing runs a
  shim from a temp directory; `TMPDIR=$RUNNER_TEMP` was the fix.
- **The host crashed twice mid-install** with an 8GB guest; 6GB was stable.
- **A crash leaves an orphan VM record** without its dataset, and the next
  claim's name collides with it.
- **An ISO has to be inside a child dataset**, readable by `libvirt-qemu`,
  and not under the runner user's private directory.
- **One runner is a single point of failure.** It went offline on
  2026-10-01, and every run after was cancelled.
